# D4: local rule editing and private draft exchange

Status: implementation and Windows/Ubuntu CI complete.
The existing shared editor now edits desktop project drafts through restricted
main-process commands. MQTT still exposes read requests only. No real system,
extension installation, device command, upload or activation was involved.

## Local workflow

Create/open a project, select a system and choose **Local draft** in the MQTT
panel. The shared designer offers device, clock and solar triggers; device,
weekday and time-window conditions; ordered set/toggle/scene actions; colors;
reusable leaf-action sequences; rule copy/delete and directed sender grants.
New rules and copies start disabled. Enabling a rule in a local draft does not
activate it remotely. Apply changes to local memory, then explicitly save the
project. The stored Z2M snapshot remains separate and read-only.

Device-dependent changes require a fresh catalog with the exact device/property
access bits, values, numeric bounds and scene target/endpoint. A readable sensor
does not become an actuator. Group capabilities are not inferred from members;
confirmed group scenes can be used. Cross-system conditions and actions require
unique base topics and explicit partner declarations in both local drafts.
The device's Z2M system and broker are selected separately in the desktop form;
triggers remain local. These local grants do not establish installed runtime
permissions. Existing unknown device fields are not silently reinterpreted.
Rename-only edits preserve unchanged actions without requiring a live catalog;
new/changed device actions and enabling a rule require confirmation again.

Writable binary or discrete `state`/`state_<channel>` properties with confirmed
`ON` and `OFF` values also offer native `TOGGLE` in the desktop value selector.
This write-only choice is not added to trigger/condition values or inferred for
other properties. It stays in the same `set` command with any brightness, colour
or other values and uses the existing pinned extension's native Z2M dispatch.
The separate cache-based `toggle` action retains its existing semantics.

Capability failures identify the automation or sequence, section, entry and exact
property, including the owning system and device. Feedback displays the submitted
value with its type and the permitted comparisons, discrete values, numeric bound
or increment, colour format or toggle action. Whole-draft checks collect up to 20
distinct findings, including disabled rules, and mark omitted findings explicitly.
Corrective navigation opens the matching entry and focuses the specific action
value even when a command sets several properties. These bounded details appear
only in local UI feedback; recordings contain no private values. Remote feedback
keeps its existing value-free allowlist and cannot inject capability context.

Rules retain their IDs during edits. Copy creates a new protocol-compatible ID
and disables it. Early D2 incomplete drafts remain readable; their unconstrained
UUID IDs and incomplete bodies may fail the stricter schema. Copy such a draft,
complete the copy in the editor, then explicitly delete the old incomplete entry
before exporting. No automatic ID rewrite changes existing references.

Rules allow up to eight triggers, sixteen conditions and sixteen action steps.
Up to 32 sequences contain leaf actions only. Expansion, missing references and
combined call/first-step delays are checked; expanded plans remain within sixteen
steps and each effective delay within 86,400 seconds. Referenced sequences cannot
be deleted. Editing a sequence also checks affected callers. Names, IDs, order,
retrigger/restart policies and partner declarations remain explicit data.

## Input preservation and conflicts

Every designer command names its system, project generation and a digest of the
draft and relevant catalog/topology/grants. Changed state rejects an old editor
request. Bounded request-ID replay handling prevents duplicate local mutations.
Successful edits increment only the local revision. All project changes still
use the existing size checks, external-file conflict checks and atomic saves.

Language/theme changes and background reads preserve the open editor. Desktop
temporary editor state is scoped by project/system and survives renderer reload
within that application session. Applying or canceling clears it. An open editor
blocks project saving and participates in the close/discard warning, independently
of unfinished project-setting forms. It is not an app-restart recovery promise.
System views keep separate selection/search state; a modal editor captures its
original system and cannot apply to another project's replacement generation.

## Symcon draft import and export

Expand **Draft import and export**. The destination is the system currently
selected in the shared designer. Use its local view for file import/export, or
copy the stored snapshot into a local draft. Native main-process choosers select
all files; paths and file operations are not exposed through renderer IPC.

Import accepts a single UTF-8 YAML 1.2 or JSON configuration document, including
the YAML draft shown by the Symcon editor. It is not a Symcon kernel migration
archive, event-object export or native-variable permission export. Unsupported
fields and Symcon references are rejected. No sibling clone or running Symcon
installation is needed. Keep source exports private and outside repositories.

Before replacement, a native dialog shows old/incoming rule counts, sequence and
grant counts and the disabled-import policy. A separately selected private
`.z2ma` project backup is mandatory. Canceling or a failed backup leaves the
draft unchanged. Incoming rule/sequence IDs and action order are retained;
incoming rules are disabled. Stored YAML/checksum and remote operation are not
replaced. Export produces YAML from the local configuration, checks the complete
schema and sequence references and cannot overwrite the active project path.
Existing export destinations receive a `.bak` through the shared atomic writer.

Imports and exports are bounded to 1 MiB; duplicate keys, aliases, multiple documents,
unknown tags and unsafe/private fields are rejected. These checks establish a
supported local document, not full device/runtime validity. Offline imports may
contain devices absent from the current catalog; later device edits and D5
transfer validation must check them. Replacing/importing local data does not
send MQTT and does not implicitly save the active project.

Step 5 shows rule, enabled-rule and sequence counts for the local draft and the
stored snapshot separately, including while viewing the stored source. Their
revision counters are independent. The mandatory pre-import backup contains the
previous draft; choosing that backup does not change the active project's save
destination. Save the project after importing to preserve the new draft.
Regression coverage adopts two replacement rules, including a 30-second false
sensor trigger, then saves and reopens through a new project service. The old
draft stays in the backup, incoming IDs/timing survive, and disabled local flags
remain separate from the stored permissions.

## Schema ownership and evidence

The application consumes the canonical schema artifact from
`Symcon_Z2MAutomations/libs/z2m/automations.schema.json` at commit
`369e2808270e2d1eedb9f6bd932ac9250daf5a3c`. It adds an optional `system` base
topic to device-value conditions. Its provenance and SHA-256 are recorded
in `apps/desktop/schema/provenance.json`; build and tests verify integrity.
This is not a separate editable runtime/schema fork. AJV 8.20.0 evaluates its
draft-07 schema without coercion/removal; YAML 2.9.1 handles bounded private file
exchange. Both run in main and are pinned by the lockfile. No dependency enters
the shared browser designer or preload.

The 53-test suite includes stale/idempotent local writes, malformed schema and
values, zones, access direction, scene endpoints, directed partner grants,
sequence expansion/deletion, restricted IPC, private YAML, canceled import,
mandatory backup, preserved stored state and schema provenance. Electron smoke
adds actual main/preload/renderer editing, language changes, temporary-input
recovery after renderer reload, applying a draft and saving a scene sequence.
The independent MQTT peer verifies that the combined workflow sends read requests
only. DE/EN catalogs, types, integrity and six viewport/theme layouts are checked.

Local Windows `npm run verify` passed all 53 tests and type/catalog/integrity
checks. `npm run smoke`, `npm run make`, `npm run smoke:packaged`,
`npm run pack:designer` and `git diff --check` passed. Both source and packaged
Electron smoke passed the combined D1–D4 workflow. The packaged dependency
check verified all 51 production manifests, including the application.
[CI run 42553084613](https://github.com/Burki24/Z2M-Automations/actions/runs/42553084613)
closed D4's platform CI scope for commit `dae69b8`. Windows passed 53 tests and
Ubuntu 24.04 passed 52 with the Windows-only lock test skipped. Both passed

Actual native dialog interaction, installed Ubuntu,
26.04/Wayland and real Z2M/Symcon coexistence remain separate acceptance. D5 still
