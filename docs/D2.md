# D2: local projects, drafts and protected credentials

Status: implementation and platform CI complete on 2026-11-08. Native Ubuntu
secret-service/dialog acceptance remains open. D2 contacts no broker, Symcon
instance or device; subsequent read-only connections are documented in [D3](D3.md).

## User workflow

Expand **Local project**, then create a project or open a `.z2ma` file through
the native file chooser. The initial synthetic examples are a separate view;
creating a project starts with no brokers or systems.

1. Apply a project name.
2. Add a broker using host, port and TLS. This stores connection settings only.
3. Add systems, each assigned to a broker and a distinct base topic. A project
   supports at most eight brokers and eight systems; systems may share a broker.
4. Create, rename, copy or delete local rule drafts for an explicitly selected
   system. New drafts and copies are disabled. Deletion requires confirmation.
5. Save the project, save under another name, or export a portable copy.
6. Explicitly choose OS-protected or session-only storage, then import a private
   credential JSON file through the system chooser. The application does not
   connect automatically. Only main reads this file; the designer never receives
   a username or password.

The private credential file must contain exactly two string fields, `username`
and `password` (an empty username is allowed). It is bounded to 16 KiB and must
remain outside the repository and portable project. Import leaves the original
file unchanged; the user controls its subsequent storage/removal. The application
never creates a plaintext credential file in normal operation.

Apply buttons accept forms into the in-memory project. Save writes accepted
changes to disk. Unfinished forms block save/export, survive language/view
changes, and can be explicitly discarded. Non-secret unfinished fields also
survive renderer reload in bounded session storage. Passwords are never placed
there. Closing, creating or opening with unsaved work asks before discarding it.

Existing rules and sequences retain their IDs and enabled flags on round trips.
The full device/time/condition/action editor and Symcon draft import remain D4;
D2 creates intentionally incomplete, disabled local drafts. These are not
validated runtime configurations. Stored Z2M state is unknown and operation is
disconnected throughout D2.

## Portable format and file operations

The UTF-8 JSON envelope has `format: "z2m-automations-project"`, `version: 1`,
stable project ID, name, broker records and system records. Each system has its
own draft configuration and optional known baseline revision/SHA-256 checksum.
New systems have no baseline. Changing broker endpoint, broker assignment or
base topic invalidates the associated baseline while preserving local drafts.

Validation rejects unsupported format versions, extra envelope fields, invalid
references, duplicate system IDs/bindings, oversized or malformed files, unsafe
JSON keys and credential/session/Symcon-reference fields. Files are bounded to
2 MiB; configuration nesting, collections and strings are also bounded.
These project checks do not replace the later Z2M schema/capability validation.

Writes use a unique sibling temporary file, flush it, then rename it into place.
Before replacement, the previous file is saved as `.bak`. Failure leaves the
in-memory draft intact; temporary output is cleaned. Save checks the current
file hash against the opened/saved version and rejects external modifications
or deletion. Save As can preserve a separate local version after a conflict.
Export does not change the active path or mark drafts saved; exporting onto the
active path is rejected to avoid bypassing conflict detection. Normal OS chooser
overwrite confirmation applies to explicitly chosen destinations.

Restore reads the last `.bak` into dirty local memory after confirmation. It
does not replace the current file or change anything in Z2M. Backups are private
local project data and must not be committed. The hash check is optimistic
conflict detection, not a distributed lock against non-cooperating writers.

## Credential boundary

Main owns the vault under the application user-data directory. Records use
hashed project/broker identifiers and contain OS-encrypted values bound to the
broker ID, host, port and TLS setting. A record cannot be reused for a different
project or endpoint. Credential IPC accepts only broker ID and storage mode;
file selection, parsing and encryption stay in main. No password fields or
credential-read operation exist in the designer. Main returns storage status
only. Project exports and
diagnostics contain neither credentials nor private certificate keys.

Windows uses Electron's asynchronous safeStorage API backed by DPAPI. Linux
requires an available keyring and an explicitly recognized backend; `basic_text`
and unknown backends are rejected. On the pinned Electron 45, async availability
alone does not prove keyring protection. The Linux adapter therefore uses the
guarded synchronous API and its backend check; it never enables plaintext mode.
This compatibility choice must be revisited before moving to Electron 46, where
the synchronous API is scheduled for removal.

Unavailable or locked protection fails without writing a fallback file. The
user may explicitly select session-only storage. That choice removes older
persistent credentials for the broker. Session values disappear on restart,
project open/new or restore. Explicit removal clears both stores. Protected
records survive app restart but are deliberately absent from portable exports.
OS user isolation is not protection against all other apps running as that user.

All file paths come from main-process system dialogs. The bridge offers fixed
project and credential commands, not arbitrary filesystem, shell, MQTT or secret
read operations. Main serializes project/vault operations. Diagnostics use the
existing bounded sanitizer with fixed event/operation keys and request IDs; no
project names, hosts, file paths, file contents or secret values are recorded.

## Evidence and remaining checks

The 28-test suite covers project round trips, unsupported/oversized/malformed
input, ownership/reference constraints, backups, restore, exports, conflicts,
failed replacement cleanup, a real Windows exclusive file lock, endpoint changes,
credential isolation/encryption, absent/basic-text/locked keyring cases, explicit
session mode, secret removal, bounded credential import and IPC rejection.
Protector tests use synthetic
authenticated encryption; they are not native Linux keyring acceptance.

Real Electron smoke exercises the new forms, language/view input preservation,
disabled draft creation/copy, file save/reopen/restore through the main-process
service, main-only credential import, session credentials, real OS-protected
storage when available, keyboard
focus traversal and mouse-wheel scrolling. It also checks six viewport/theme
combinations and screenshot capture. Smoke file choosers and confirmation results
are fixed to synthetic files in the temporary test profile; production uses
native dialogs. This does not establish manual native-dialog acceptance.

Windows build, type/catalog/integrity checks, all 28 tests, Electron smoke,
`npm run package`, packaged-app smoke and `npm run pack:designer` passed locally.
The renderer reload test also confirms recovery of unfinished non-secret form
input. Initial native input-injection checks exposed focus/scroll synchronization
in the test harness; it now focuses web contents, waits for input processing and
sets the pointer and wheel scrolling permission explicitly. Both source and
packaged smoke have passed; Ubuntu behavior still requires CI evidence.

This closes D2 implementation/CI, including the installer-build evidence left
