# D6 – Activation and operation

## Operator workflow

The selected automation shows the Z2M networks required by its remote device
conditions and actions, including reusable sequences. Red means confirmed stopped,
yellow means unknown and green means confirmed active. Each known destination
opens that network's Operation page directly. A return button leads back to the
original network. The Operation page lists destinations used by released stored
rules and explains the order: choose permissions, activate the receiving networks,
then activate the source. Navigation never starts or uploads anything.

Activation confirmation lists the saved rules that will become active. A network
with saved partner permissions can instead enable **Partner reception** with
zero released local rules; the confirmation explains that only partner reception
is being enabled. Networks with neither released rules nor saved permissions
remain blocked. These indicators confirm runtime state only, not MQTT bridge or
ACL correctness or physical device effects.

Open **Operation** and choose a system. The rule list and
execution status come from the stored revision. A single run can execute a
disabled stored rule. The extension evaluates conditions, dispatches local and
permitted remote device commands and reports the result.

Content changes are stored with all rules disabled. **Operation** displays the
freshly confirmed enabled/total count and explains why starting is blocked when
none are enabled. Select the desired stored rules in the sorted, scrollable list
and choose **Check and apply rule permissions**. Main checks the exact stored
revision, validates switch-only changes, asks for explicit confirmation and
creates a private backup before stopping operation and storing once. Independent
readback confirms the result. Confirm **Activate automatic operation** separately.
The permission status uses text and the desktop palette: red **Not confirmed**
for a changed/stale selection or a rejected check; yellow **Unknown** while
disconnected, reading, applying or reconciling an unresolved transfer/update;
green **Confirmed** when the selection matches freshly confirmed Z2M permissions.
Confirmed permissions may include disabled rules. This status makes no claim
about operation being stopped or active; the live operation status is separate.

Direct permissions change the stored rules without uploading unrelated draft
content. A local draft matching the previous stored configuration is synchronized
after success; a divergent draft is preserved. Canceling confirmation or backup
leaves its input and running operation untouched. Pending selections survive
language/system changes and renderer reloads within the application session.
Changed contexts require an explicit selection refresh. Unconfirmed transfers
block starts and offer read-only reconciliation without command replay.

The existing draft/check/step-8 workflow also recognizes switch-only edits.
The restart recovery option defaults to off and resets when selecting another system.

Use **Stop selected run** for a specific in-progress run, or **Stop all
operation** to stop automatic operation and all runs and prevent restart recovery.
Extension 0.2.0 and the bundled 0.2.2 preserve the saved restart preference, but
persist an inactive intent and report `resume_status: stopped`; this is a confirmed
stop even if `resume_enabled` is still true. Clearing the UI checkbox affects the
next activation request rather than editing this saved preference directly.
An independently verified stop can confirm a lost reply without retransmission.
Closing the desktop application disconnects the MQTT client and leaves the
extension in charge of automation.

## Safety and diagnostics

Main-process confirmation identifies the system, broker, topic, revision,
rule and run as applicable. Starts require fresh session and revision evidence,
a one-use challenge and independently correlated readback. A lost reply never
causes retransmission. If a start has an uncertain outcome, further starts on
the endpoint are blocked for this app session until a system stop is confirmed.
The user can read the current status before deciding to stop.

Use the desktop diagnostics recording controls to capture bounded execution
observations with system, rule, run, state and step. This records the snapshots
the extension publishes and may omit intermediate transitions that the
extension coalesces. A result confirms extension-side execution status.
Physical device state is outside that acknowledgement.

## Verification

Loopback MQTT tests use the pinned extension artifact and synthetic Zigbee
devices. They cover dispatch, one- and multi-system selection, enabled-flag
validation, exact-run stop, restart recovery with both settings, missing
acknowledgements and continued extension operation after the desktop client
disconnects. The canonical extension suite separately covers shared targets,
blocked targets and isolated branch failures, including eight-system routing.
Live Zigbee2MQTT, physical devices and Ubuntu desktop acceptance require
separate verification.
