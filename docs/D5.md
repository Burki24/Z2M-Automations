# D5 extension installation and storage

Use the MQTT panel to select the target system. The panel displays the installed
and bundled build identifiers. The bundled Extension 0.2.2 is the canonical
generated artifact from Symcon commit
`369e2808270e2d1eedb9f6bd932ac9250daf5a3c`. Its provenance records the artifact,
build and schema checksums. Build staging and the desktop main process verify the
artifact before use. The desktop app sends it as data to Zigbee2MQTT.

## Workflow

- **Install bundled extension** in workspace step 4 handles the complete update.
  Confirm the target, build and Z2M restart, and choose a private backup location
  when stored rules exist. The app confirms a stop of automation operation,
  uploads the pinned extension, requests one Z2M restart and waits up to 90 seconds
  for a live offline/online cycle and a fresh session with the expected build.
  It verifies the exact original stored YAML, revision and checksum before
  restoring previously active automatic operation and its restart preference.
  Previously stopped operation stays stopped; interrupted runs are ended.
  Local drafts and stored rule flags are not uploaded or changed by this action.
  Keep Zigbee2MQTT running initially; the app uses its live MQTT save and restart
  endpoints. The app account needs permission for `bridge/request/restart` and
  `bridge/response/restart` under the system base topic as well as extension
  management topics. An initial installation also requires a confirmed extension
  list without our extension. An already current build is a read-only no-op.
  Progress and stage-specific failures remain visible in the extension panel.
- **Validate for Z2M** compares fresh storage against the local draft baseline.
  It checks the schema and fresh catalogs, including stored receiver grants for
  partner targets. It prepares an exact YAML candidate with the next remote
  revision and all rules disabled. The extension must confirm its checksum,
  revision and rule count. The draft remains available for further editing.
- **Store disabled rules in Z2M** consumes the validation receipt. It checks the
  connection, session, build, draft and remote baseline, shows the changed IDs
  and requires confirmation. Replacing existing storage requires a private
  project backup. It checks the receiver again after the dialogs, sends one
  request with the expected revision and session, then checks the acknowledgement
  and independently reads the stored YAML, revision and checksum.
- **Check transfer / Check update status** reads after an ambiguous result.
  Missing replies can be reconciled with independent fresh evidence. Update
  checks never send control commands. After a confirmed partial update, the
  installation button asks for confirmation before continuing unsent stages.
  Sent stop, upload, restart and activation commands are never replayed.
  Unresolved attempts are tracked in memory during the app session; a fresh
  MQTT connection alone does not clear them.
  Manual activation and one-shot starts on that system remain blocked until
  its update is resolved; status reads and explicit stop commands remain available.

An active runtime or armed restart recovery blocks configuration storage. A
confirmed stopped intent is safe even when the saved restart preference is true.
Extension updates explicitly stop first and restore only the previous automatic
operation after verification. MQTT requests use exact
topics, transaction IDs, connection generation checks, QoS 0 and no retention
or offline queue. Validate and store use the extension's 128 KiB YAML limit.
The canonical store request guards session and revision. Bridge installation
uses the bridge's save endpoint, which has no atomic precondition for the prior
build. Coordinate installation with other management clients.

The first background observation can initialize the baseline. Later observations
update the stored view without moving the draft baseline. A mismatch blocks
validation and storage, displays changed IDs, and offers a private backup
containing the local draft and fresh stored configuration. After reviewing the
backup, use the explicit D4 adoption workflow to establish a new baseline.
Confirmed storage also advances the baseline. Save the project to persist it.

## Verification

The isolated loopback peer covers exact disabled YAML, revision and checksum
confirmation, backups, cancellation, stale revisions, session changes after
confirmation, lost replies without retransmission, first installation with the
pinned bytes, and discarding an old observation queued before a confirmed write.
Windows verification passed 60 desktop tests, the NSIS installer build,
packaged Electron smoke and the shared designer archive build. The canonical
extension passed its build check and 28 build/runtime tests. Electron smoke
exercises the synthetic read and local-edit workflow. Windows and Ubuntu 24.04
CI passed in [run 42557311324](https://github.com/Burki24/Z2M-Automations/actions/runs/42557311324).
Native dialog interaction and real Zigbee2MQTT compatibility remain separate
practical tests.

The update regression uses the frozen, checksum-verified canonical 0.2.0 artifact
and the bundled 0.2.2 artifact with isolated MQTT peers and synthetic devices.
It reproduces the former false stop failure: `resume_enabled` remains a saved
preference while `resume_status: stopped` prevents restart recovery. Tests cover
update ordering, both recovery preferences, unchanged backup/storage, stopped
operation, cancellation, missing acknowledgements, rejected commands, absent
or retained-only restart evidence, wrong builds and changed storage. This is
protocol evidence on Windows, not a live Z2M service or Ubuntu acceptance run.
The peer request deadline is two seconds because real extension commands persist
state on disk. Delayed-activation regressions cover preparation and restoration;
bounded diagnostics report only operation names and elapsed milliseconds. Run
43159085338 passed the complete Ubuntu job but exposed the former 100 ms test
deadline on Windows before packaging. Both error patterns were reproduced locally with
250 ms delays; a new Windows CI run must confirm packaging and the EXE upload.
`npm run test:extension-update-ui` checks renderer progress during the pending
action, DE/EN feedback, stopped-intent storage eligibility and confirmation
scroll boundaries in both themes. It inspects DOM/layout only and captures no images.
