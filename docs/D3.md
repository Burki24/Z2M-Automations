## Workflow and boundaries

Create/open a local project, configure brokers and assign up to eight systems
using distinct base topics per broker. Import credentials through the existing
main-only file chooser if required. Expand **MQTT** and explicitly connect a
selected broker. Opening a project never connects automatically. Systems on one
broker share one connection; separate brokers retain independent connections.

The panel shows connection/read freshness, extension status and device/scene
catalogs. Choose local drafts or stored Z2M configuration in the designer.
Reading preserves local drafts, enabled flags and unfinished forms. A confirmed
read updates a separate stored snapshot and baseline, marking the project dirty
when those change. Save explicitly to preserve the snapshot. Disconnect retains
the last read as stale and removes confirmation of active operation.

MQTT.js 5.16.1 runs only in main. Restricted IPC exposes connect, disconnect,
refresh, view and certificate selection/status commands. It has no arbitrary
topic/payload publishing, upload, installation or device-control operation.
Requests use only our extension's `status` and `editor` operations. Neither
reading nor changing the displayed source starts or stops automations.

TLS validates the server chain and hostname with TLS 1.2 or later. System trust
works without importing additional material. For a private CA or mutual TLS,
import a private UTF-8 JSON bundle through the main-process file chooser:
`ca` contains PEM CA certificates; `cert` and `key` are a paired PEM client
identity; optional `passphrase` unlocks its key. Only those fields are accepted.
The bundle is limited to 192 KiB, each field to 64 KiB, and is validated by Node's
TLS context before use. No verification bypass exists. Certificate material is
session-only, outside portable projects, renderer state and diagnostics. It is
cleared on project replacement or endpoint changes. The source file remains
under the user's control. Username/password protection remains as in [D2](D2.md).

## Protocol and stored data

Exact per-system subscriptions cover bridge state, extension status and the two
read-response topics. A read uses correlated status/editor/status transactions
and requires matching protocol, schema, session, revision and SHA-256 checksum.
Retained replies, foreign topics, wrong/expired transactions and superseded
connection generations cannot confirm data. Subscription and response waits are
bounded. Reconnection performs fresh reads with new transactions. QoS 0,
non-retained requests, disabled offline queues and explicit resubscription avoid
replaying requests. MQTT client IDs are independent of other management apps.

Catalog parsing preserves stable system/device/scene identities, typed access
metadata and scene endpoints. Unknown permissions remain unavailable; group
capabilities are not inferred from a member. Catalog limits are 256 devices,
256 groups and 512 scenes per response. Public diagnostics use the existing
bounded sanitizer and fixed event/error codes with correlation IDs. They exclude
raw responses, device contents, YAML, broker names/hosts and secrets.

Project format 1 gains an optional per-system `stored` snapshot containing the
exact source YAML, its parsed configuration, revision and checksum. Existing D2
projects remain readable. Local draft `configuration` stays separate. YAML is
hashed without changing comments or line endings and is limited to 1 MiB per
system; the complete project remains limited to 2 MiB. Oversized observations
fail without replacing local data. Session and activation tokens are never
exported. Endpoint or binding changes invalidate the stored baseline and cache.
Configuration shape and transport identity checks are not the complete runtime
schema/capability validation planned for D4/D5.

## Verification and remaining acceptance

The 45-test suite includes real MQTT.js against an independent loopback-only
MQTT 3.1.1 peer: eight shared systems, separate brokers, ownership, retained and
late replies, missing/denied subscriptions, timeouts, session/checksum changes,
reconnection, locked credentials and authentication rejection. Actual TLS tests
cover private CA validation, wrong hostnames and mutual client authentication.
Certificates are generated temporarily with OpenSSL; no private keys are
committed. Portable snapshot round trips preserve drafts and exclude sessions.

Electron smoke also exercises the UI/main/MQTT path with an ephemeral isolated
peer, stored/local view switching, catalogs, disconnect state, language/input
preservation and rejection of control operations. Both source and packaged
smoke use only synthetic data. Native dialog interaction is still a separate
manual acceptance task.

Packaging initially exposed a hoisted-workspace dependency omission: a built
installer did not contain MQTT.js. Forge now stages the installed production
dependency closure, including original licenses, without install scripts or
network access. A regression test checks staging; packaged smoke independently
checks every production manifest dependency inside ASAR before opening the app.
This prevents accidental resolution from the surrounding checkout.

Windows `npm run verify` passed all 45 tests, types, catalogs and integrity
checks. `npm run smoke`, `npm run make`, `npm run smoke:packaged`,
`npm run pack:designer` and `git diff --check` passed locally. Packaged smoke
verified all 45 production manifests, including the app, inside ASAR. The
unsigned setup was generated under `apps/desktop/out/make` using process-local
temporary directories on E:.

One packaged smoke run concurrent with installer creation failed because its
native wheel event was not received. The sequential run after packaging passed;
the underlying intermittent input-delivery cause is not established. CI keeps
packaging and smoke sequential. This remains a test-harness observation, not
evidence of manual mouse-wheel acceptance.

CI now runs packaged smoke on Windows and
Ubuntu 24.04 as well as source smoke. A local Windows pass does not complete
Ubuntu desktop acceptance. Real Linux keyring/dialog checks,
Ubuntu 26.04, Wayland/X11 and installed-app acceptance remain open. Real Z2M
coexistence and practical tests require a separate explicit request. Full local
editing is D4; validation/storage/installation and operation remain D5/D6.
