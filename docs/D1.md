# D1: shared desktop foundation

Status: D1 complete on 2026-11-08 for the offline foundation and CI scope.
Both platform jobs passed from the same source commit; installed desktop
acceptance and general operating-system support are not established by CI.

The application uses Electron 45.2.3, Electron Forge 8.0.1 and TypeScript 7.0.2,
pinned through package-lock.json. Build tooling uses Node 24.20.0. The full
application is licensed under PolyForm Noncommercial 1.0.0, as confirmed by the
owner. The initial shared designer retains its original notice.

## Available behavior

- One offline application with the canonical designer and local DE/EN catalogs.
- Two isolated synthetic systems, each with its own disabled example rule and
  device identities. Selection and language changes preserve the search input.
- Responsive light/dark layout and localized, opt-in diagnostics: at most 200
  events and one minute; reads and repeated starts do not extend the end time.
- Sandboxed renderer, context isolation and a fixed preload bridge for reading,
  selecting an example system, language audit and recording control.
- Every IPC request checks the owned main frame, exact local origin and payload.
  The local protocol serves only staged assets; network navigation, downloads,
  permission requests and additional windows are blocked. No general file,
  shell, raw IPC, MQTT or publishing API is exposed to the renderer.
- Forge targets a Windows setup EXE and an Ubuntu .deb from the same sources.
  Application/package versions are read from version.json when building.

This foundation neither connects to brokers nor creates/persists user projects.
The example rules cannot execute. These are subsequent milestones, not hidden
features of the current executable. No PHP or Symcon runtime is bundled.

## Source handoff

The canonical UI now lives in packages/designer/src. Symcon uses a versioned
archive with asset hashes and license/provenance, checked into its repository.
Neither product requires a sibling checkout at runtime or when verifying its
own committed inputs. See [the package contract](../packages/designer/README.md).
The extension/schema remain canonical in the Symcon repository, unchanged by D1.

## Verification

Local environment: Windows 11 Pro Insider Preview, build 28120, x64; Node
24.20.0 / npm 11.19.0. This is not evidence for every Windows 11 release.

Windows verification exercises the real isolated Electron renderer and the
packaged application: both systems, DE/EN switching, input/configuration
preservation, supported bridge keys, rejected invalid requests, debug start/stop
and 360/1920/3840-pixel layouts in both themes. Unit tests independently cover
sender/payload rejection, protocol paths, bounded recording and automatic expiry.
The Windows setup is unsigned and is built for development only; it is not an
installed-app acceptance or a release.

The desktop workflow runs the same build/check/test/package/smoke steps on
windows-2025 and ubuntu-24.04. Linux uses Xvfb and the Chromium sandbox configured
only inside the disposable CI runner. It never disables the renderer sandbox.
The first [desktop CI run](https://github.com/Burki24/Z2M-Automations/actions/runs/42377767843)
tested source commit `dbcd466c7a0259cbe2d2bc71caa9703e453917f5` on 2026-11-07.
Windows passed all steps. Ubuntu passed compilation, checks, six contract tests,
`.deb` generation and the functional renderer assertions (`DESKTOP_SMOKE_OK`),
then failed with `UnknownVizError` before the final layout marker. The remaining
asynchronous capturePage call is the likely failing boundary; the original log
did not identify individual layout/capture phases.

The follow-up keeps the Linux smoke window mapped on a 3840x2160 Xvfb display,
so capturePage has a visible rendering surface. Windows smoke remains hidden.
Per-viewport and capture markers now identify the failing phase, and an empty
capture fails explicitly. No sandbox setting is relaxed and no failed capture
is ignored. The subsequent run still failed at `DESKTOP_CAPTURE_START` with
`UnknownVizError`; mapping the window alone did not fix capture.

Local follow-up on 2026-11-08: `npm run verify` passed all six tests and
`npm run smoke` passed all six viewport/theme combinations and non-empty image
capture on Windows. Chromium reported GPU-cache warnings; the runtime assertions
and image capture succeeded. The first `npm run make` attempt failed with
`ENOSPC` because the system temporary volume C: was full; this is an environment
failure, separate from the Ubuntu rendering issue.
Repeating the build with process-local TEMP/TMP pointing to the ignored
`apps/desktop/out/build-temp` directory on E: succeeded, including the unsigned
Windows installer. The newly packaged executable also passed `npm run smoke`
with `Z2MA_SMOKE_BINARY` set to its path. No system settings were changed.

No Ubuntu/WSL distribution is available locally. Native Wayland/X11 desktop
acceptance and the additional Ubuntu 26.04 run remain unverified. These remain
separate from the completed D1 CI scope; installed-app acceptance belongs to D7.

## CI follow-up: 2026-11-08

[Run 42470140921](https://github.com/Burki24/Z2M-Automations/actions/runs/42470140921)
failed on both platforms while downloading Electron: HTTP 504. Earlier Ubuntu
runs also failed during packaging downloads and at screenshot capture
(`UnknownVizError`), after passing functional and viewport assertions.

Setup now retries only transient downloads, at most three times. Setup and Forge
share the same cache and Electron's pinned checksums; CI caches the downloads.
Linux CI smoke selects software rendering before startup. Normal launches keep
their settings, the sandbox stays enabled, and capture remains mandatory.

Local Windows verification passed: setup, 13 tests, types, source/package checks,
unsigned installer generation, renderer capture and packaged-app smoke.
The first local smoke hit its deadline at capture; the repeat with process-local
TEMP/TMP on E: passed. Packaging also reproduced HTTP 504 before adding the pinned
checksums, then passed using the existing verified ZIP. No global settings changed.
The following successful run verifies these fixes within the CI environment.
No Live system changed.
